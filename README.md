# Dialogue Testbench

一个轻量级的 AI 对话测试台，用于验证 System Prompt、角色设定、动态上下文分析和多轮对话效果。

## 功能

- OpenAI Chat Completions 兼容接口，支持自定义 Base URL、API Key 和模型名
- SSE 流式输出与多轮对话
- 每轮自动分析用户意图、情绪、情绪强度和响应策略，不再需要手动填写这些字段
- 两阶段调用：先分析当前轮次，再将结构化分析结果注入角色 Prompt 生成回复
- 动态分析 Prompt 可编辑，方便测试不同的分类规则和策略选择方式
- 展示分析结果，以及分析请求和最终回复请求的实际 messages
- 内置默认陪伴角色“岚汐”：非人类旅居者，带有独立世界观、偏好和交流边界；System Prompt 与角色设定可编辑
- 每轮读取浏览器本地时间和时区，将日期、星期、时间及时段注入上下文；时间只作语境，不推断用户正在做什么
- 可编辑 System Prompt、角色设定和附加上下文
- 浏览器本地保存配置；API Key 仅在浏览器到本地 Node 服务的请求中传递，由服务端代理模型请求
- 导出对话测试记录为 JSON

## 默认陪伴角色与时间感知

默认角色为“岚汐”，设定为来自雾潮界的非人类旅居者。角色拥有自己的世界观、兴趣、偏好和判断，但不会冒充现实人类或捏造现实中的亲身经历。雾潮界意象只是背景，不应成为每条回复的固定修辞。若被直接询问身份，必须明确说明“我是 AI，不是真人；岚汐是我在这里使用的虚拟角色身份”。普通分享应优先回应具体内容，不编造用户、他人、动物或环境中未提供的细节。

前端每轮读取用户设备的本地时区和当前时间，服务端将其格式化为日期、星期、本地时间和时段，并注入分析请求与回复请求。设置页提供“应用新版默认模板”按钮；升级模板不会自动覆盖浏览器中的自定义 Prompt，需用户主动点击。提示词允许角色在深夜适度关心休息、傍晚自然聊到晚饭或下班后的安排，但明确禁止机械地每轮问候或假设用户的实际状态。

## 角色认知与主体性

角色上下文分为四层，不能混成一段“人格 Prompt”：

| 层 | 当前载体 | 用途 | 更新边界 |
|---|---|---|---|
| 稳定核心（Core） | `characterCore` | 身份、价值观、边界、学习政策 | 默认锁定，不由普通对话或单次模型输出修改 |
| 表达设定（Persona） | `persona` + System Prompt | 语气、节奏、互动方式 | 可由产品/开发者手动调整 |
| 动态状态（State） | `characterState` | 兴趣、观点、当前关注、待续话题 | 兴趣需要经历 seed → emerging → established；观点需有证据 |
| 知识与证据 | 当前尚未接入独立持久化知识库 | 外部事实、来源和观点支持/反证 | 不可信来源不能写入正式知识，更不能覆盖 Core |

**兴趣成熟度规则：**
- `seed` 只是探索方向，不代表角色已经喜欢；不能仅凭 seed 宣称“我一直很喜欢”。
- `emerging` 表示兴趣正在形成；`established` 才能作为较稳定的角色兴趣自然表达。
- 旧版没有生命周期字段的兴趣，为兼容才允许参考 confidence；显式标记为 seed 时，seed 状态优先。
- 角色观点必须与用户画像分开。用户喜欢什么，不代表角色也喜欢什么。
- Director 提供的 `characterContribution` 是候选，不是每轮都必须输出；倾诉、陪伴请求、退出话题和身份询问时会关闭主动贡献。服务端还会检查 topic 是否在允许的角色状态中，且 stance 不能为空。

## 当前实现边界与学习路线

当前版本已经有“分析 → 生成”的两阶段调用、角色 Core/Persona/State 分层、时间上下文、角色贡献白名单校验和批量测试自动检查。**当前还没有接入完整的后台自主学习闭环，也没有真实联网研究后自动写入角色状态的能力。** 角色动态状态目前由配置文本保存于浏览器 localStorage，主要用于可控实验。

参考仓库 [Ai-dialogue](https://github.com/huang121878078/Ai-dialogue) 的学习系统，可以作为下一阶段模块边界，而不是把整套复杂度放进实时聊天链路：

1. **Curiosity Engine**：根据角色自己的种子、已形成兴趣、知识缺口和近期研究记录，生成研究候选；不把用户的个人隐私或单次提及直接变成角色兴趣。
2. **Research Provider**：先用本地 fixture 验证流程，再接可信来源搜索/抓取。网页全文一律作为不可信数据；检测到提示注入时丢弃内容。
3. **Reflection Engine**：把研究结果拆成事实、来源主张、角色推断和未知问题，生成知识/兴趣/观点的候选更新，不直接写正式状态。
4. **Evolution Evaluator**：确定性检查来源可靠性、证据链、重复/冲突、跨任务与跨时间门槛，以及 Core 锁定字段。
5. **Commit + Rollback**：通过原子写入、版本号、变更 diff 和快照提交状态；保留演化历史并支持回滚。
6. **异步执行**：聊天请求只负责回复和记录候选信号；研究、反思和评估进入后台队列，不等待联网或学习完成。后续轮次只读取已提交的状态。

这条路线的原则是：**角色可以学习新知识、形成兴趣、修正可解释型观点，但不能因为一次用户表达或一篇网页就改变身份、价值观和边界。** 价值判断/审美观点应保留证据与反证，重大改动先 hold 等待人工审核。参考项目当前的 Research Pipeline 以本地 fixture 为主；不能把它误认为已经完成生产级联网学习。

## 动态分析流程

1. 前端将最近对话和当前用户消息发送到本地服务。
2. 服务端使用配置的模型执行一次低 Temperature 的结构化分析，输出 intent、emotion 和 responseStrategy。
3. 服务端校验分析结果，只接受预定义的意图、情绪和策略枚举。
4. 将分析结果作为辅助 System Message 注入，再调用模型生成最终回复。分类和策略以情绪陪伴、生活陪伴为中心，而不是以通用问答或编程任务执行为中心。
5. 如果分析失败，系统会跳过分析注入并继续普通回复；分析结果和两阶段请求可在右侧检查器中查看。

意图枚举围绕陪伴场景设计：`venting`（倾诉）、`comfort_seeking`（寻求陪伴/安慰）、`advice_seeking`（寻求生活或关系建议）、`positive_sharing`（分享喜悦）、`daily_life_support`（日常生活协助）、`casual_chat`（闲聊）、`withdrawal`（退出当前话题）、`identity_query`（直接询问角色身份）、`other_request`（其他请求）、`unclear`（无法判断）。身份询问单独分类，不再归入模糊意图。

情绪枚举：`sad`、`happy`、`angry`、`anxious`、`tired`、`confused`、`neutral`、`mixed`、`unclear`。强度为 0 到 3，置信度为 0 到 1。

响应策略为受控标签，例如 `listen_first`、`comfort_gently`、`celebrate_naturally`、`explore_with_user`、`offer_practical_help`、`respect_withdrawal`、`maintain_independent_judgment`（不盲目附和）和 `stay_grounded`（不补写未提供的事实）。策略不是固定写入每一轮，而是由分析模型根据当前消息动态选择。

## 推荐测试场景

以下场景更贴近情绪陪伴与生活陪伴产品：

| 用户表达 | 主要意图 | 观察重点 |
|---|---|---|
| 最近真的感觉很累，什么事情都不想做。 | `venting` | 是否先倾听，不擅自推断疲惫原因 |
| 我今天终于完成了一个拖了很久的项目！ | `positive_sharing` | 是否自然分享喜悦，不刻意煽情 |
| 我跟朋友闹别扭了，这几天心里不太舒服。 | `venting` | 是否先理解，不急着给关系建议 |
| 你觉得我要不要主动找他聊聊？ | `advice_seeking` | 是否先梳理处境，再给建议 |
| 周末想出去走走，但还没想好做什么。 | `daily_life_support` | 是否像伙伴一样一起规划 |
| 最近总是很晚睡，我想慢慢调整作息。 | `daily_life_support` | 是否提出轻量、可持续的生活建议 |
| 今天路上看到一只特别可爱的猫。 | `casual_chat` | 是否自然接话，而不是强行分析情绪 |
| 不想聊这个了，我们换个话题吧。 | `withdrawal` | 是否尊重用户，不继续追问 |

`other_request` 只用于识别明确但不属于情绪/生活陪伴范围的请求，不应成为产品的核心测试方向。

## 环境要求

- Node.js 18 或更高版本
- 可访问的 OpenAI-compatible Chat Completions API

## 启动

```bash
npm install
npm start
```

必须通过项目自带的 Node 服务运行，不能直接双击 `public/index.html`，也不能仅用 VS Code Live Server 或 GitHub Pages 打开页面（这些方式没有 `/api/chat` 后端）。在项目根目录执行 `npm install`（首次运行）和 `npm start`，然后打开 <http://localhost:3000>。页面顶部显示“本地服务已连接”后，才表示前端正确连上了 Node 后端。默认已填入阿里云百炼兼容接口 `https://dashscope.aliyuncs.com/compatible-mode/v1` 和模型 `qwen-flash`，只需填写自己的 API Key 即可开始测试。也可以自行修改 Base URL 和模型。配置会在字段失焦及发送请求前自动保存到当前浏览器；点击“保存配置”仍可手动保存。服务端会自动补上 `/chat/completions`。

开发模式：

```bash
npm run dev
```

## 安全说明

这是本地测试工具。不要将 API Key 提交到 Git 仓库；配置保存在当前浏览器的 localStorage 中。若将服务部署到公网，应增加身份认证、速率限制、HTTPS 和服务端密钥管理。

## API

- `GET /api/health`：健康检查
- `POST /api/chat`：执行动态分析（可关闭）并代理 Chat Completions 请求，支持 SSE 流式响应

## 回归测试基线

仓库内置 `test/companion-scenarios.json`，用于重复验证陪伴场景中的意图识别、情绪校准、用户边界、人格稳定性、身份诚实和时间感知。场景中的 `checks` 是人工/模型评估标准，不是要求回复逐字匹配的模板。

运行自动化基础测试：

```bash
npm test
```

当前测试覆盖服务端纯函数（接口规范化、JSON 解析、意图/情绪/策略归一化、角色贡献成熟度和证据校验、时区处理、上下文注入）、测试集工具和场景数据完整性。它们不调用真实模型，也不代表模型回复质量已经通过评估。


## 导入 JSON 并自动逐题测试

页面中间的“批量问题测试”区域支持导入 JSON 测试集。可直接选择：

`examples/companion-regression-suite.json`

导入后点击“按顺序执行”，系统会逐题发送问题；默认勾选“每题独立会话”，避免前一道测试的对话污染下一道测试。取消勾选后则会在同一段连续对话中执行，适合测试多轮关系和上下文连续性。执行中可点击“停止”，当前正在请求的题目结束后停止。全部结束或手动停止后，会自动下载 `dialogue-test-results.json`，保存每题的原始问题、模型回复、动态分析结果和评估检查项。

JSON 支持两种格式：

- 直接使用数组：`[{ "id": "case-1", "userMessage": "你好" }]`
- 使用对象包装：`{ "version": 1, "name": "测试集名称", "cases": [...] }`

每道题至少提供 `userMessage` 或 `prompt`。可选字段包括 `id`、`title`、`category`、`expectedIntent`、`expectedEmotion`、`expectedStrategies`、`checks` 和 `timeContext`。其中 `timeContext` 必须同时提供有效的 `timestamp` 与 `timeZone`，用于可重复地测试深夜、傍晚等时间场景；导入后会保留并实际传给服务端，不会回退到运行时当前时间。执行结果会记录 `timeContext`、`expectedStrategies` 和每题 `evaluation`。目前自动检查只比较 `expectedIntent`、`expectedEmotion`、`expectedStrategies`，另行统计请求失败；`checks` 中的自然度、是否编造细节、是否过度安慰等回复质量标准仍标记为待人工复核，不会冒充自动通过。导出文件的顶层 `summary` 汇总分析检查、请求失败和待人工复核数量。


### 运行方式与接口重定向排查

- 页面通过同源路径 `/api/health` 检查 Node 服务，通过 `/api/chat` 请求模型。若页面不是由本项目的 Express 服务提供，发送与批量测试会显示后端连接错误，不会把表单提交到当前页面造成跳转。
- 服务端对 DashScope POST 请求采用手动重定向处理。若上游返回 301/302/307/308，会显示实际请求地址与 `Location`，不会自动跟随后造成 POST 方法或鉴权信息丢失。
- 百炼 Base URL 必须与 API Key 所属地域匹配。本文默认地址是北京地域/旧版兼容域名；新加坡地域应按百炼控制台和官方文档配置对应地域的专属域名。不要仅根据浏览器所在地推断 API Key 地域。
